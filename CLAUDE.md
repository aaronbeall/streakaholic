# Streakaholic

A playful habit/streak tracker for Android. React Native + Expo (Router), TypeScript, local-only persistence via AsyncStorage. Solo indie project. Web is used only for quick functional testing during development — not a target platform (see "No web-specific polish" guidance).

Naming: resolved as "Streakaholic" (kept as-is — user confirmed 2026-08-01, no config changes needed).

## Stack

- Expo SDK 54, expo-router (file-based routing, typed routes enabled), React 19 / RN 0.81
- State: Zustand (`app/stores/taskStore.ts`, `settingsStore.ts`, `lastImportStore.ts`) with the `persist` middleware backing AsyncStorage directly — migrated 2026-08-08 off React Context (`TaskContext`/`SettingsContext`, both deleted) specifically for selector-based selective subscription; see the "State management" section below for the full rationale and shape. `ToastContext` (ephemeral, non-persisted UI state) intentionally stayed as Context — no need for either selective subscription or persistence there.
- Animation: `react-native-reanimated` v4 (+ its `react-native-worklets` peer dep) throughout `TaskCard.tsx`/`ParticleSystem.tsx` (migrated off the legacy `Animated` API)
- Safe areas: `app.json` sets `android.edgeToEdgeEnabled: true`, so every screen draws behind the status bar and gesture nav bar. Every custom header (`HomeScreen`, `SettingsScreen`, `ArchivedTasksScreen`, and the shared `TaskHeader` used by Dashboard/Calendar/Stats) applies `useSafeAreaInsets().top` inline instead of a hardcoded `paddingTop`; every bottom-anchored element (FAB, `ToastBanner`, scroll content, the fixed-height calendar grid) adds `insets.bottom`. `AddTaskScreen` uses the native `Stack.Screen` header (already inset-aware) so it only needed a bottom-inset fix on its ScrollView. `SafeAreaProvider` itself comes for free from expo-router's root layout.
- Charts: `react-native-chart-kit` (Dashboard + per-task Stats screens)
- Icons: `@expo/vector-icons` MaterialCommunityIcons — `MaterialCommunityIconName` type is derived directly from the glyph map
- Data export/import: `expo-file-system`, `expo-sharing`, `expo-document-picker`
- Theming: `app/hooks/useThemeColors.ts` — `useColorScheme()`-backed semantic palette (`background`, `surface`, `surfaceSecondary`, `text`, `textSecondary`, `textTertiary`, `border`, `iconButtonBackground`, `overlay`, `isDark`). Every screen/component builds its `StyleSheet` via `createStyles(colors)` + `useMemo` instead of a static object. Task-specific/status/brand colors (task.color, streak red/orange, primary blue, destructive red, trophy gold) are intentionally left un-themed — they read fine on both schemes.
- Testing: `jest` + `jest-expo` preset, `npm test`. Scope is intentionally narrow — pure functions in `app/utils/*.ts` only (`streaks.ts`, `data.ts`, `importExport.ts`, `periodStats.ts`, `pieWedge.ts`, `calendarGrid.ts`). No component/render tests, no mocking of the Zustand stores/AsyncStorage — anything that needs those stays manually/on-device tested per the rest of this doc. Test files live in a top-level `__tests__/utils/` mirroring `app/utils/`, **not** co-located inside `app/`: expo-router (with `typedRoutes` on) scans every file under `app/` as a route candidate, so a `*.test.ts` sitting in `app/utils/` got bundled into the actual app and crashed at runtime in Expo Go on its top-level `describe(...)` call (`describe`/`it`/`expect` are Jest globals, not present outside a test run). `package.json`'s `"jest"` config scopes `testMatch` to `__tests__/**/*.test.ts` accordingly. No CI config present (tests are local-only for now).

## Architecture

Routing is file-based under `app/`. Each route file is a thin re-export of a screen in `app/screens/`:

- `index` → `HomeScreen`: grid of `TaskCard`s (2–4 columns responsive), streak filter bubbles, FAB to add task, empty state when no (non-archived) tasks or a filter matches nothing
- `dashboard` → `DashboardScreen`: aggregate stats + charts across all/selected **non-archived** tasks. Same shape as `task-detail` (2026-08-07): a header (back button — `router.canGoBack() ? router.back() : router.push('/')`, fixed 2026-08-07 from an unconditional `router.push('/')` that broke back navigation two ways at once: it always landed on Home regardless of what screen actually opened this one (e.g. Home → Dashboard → a task's detail via a month card → "back" skipped Dashboard entirely), and since a `push` is a forward navigation, the Stack's `slide_from_right` animation played forward instead of reversing, so `back` visually looked like advancing, not returning. `TaskHeader`'s own back button had the identical bug and got the identical fix. `canGoBack()` still falls back to Home for the edge case of landing on either screen with no history at all (e.g. a fresh deep link). Two related fixes in the same area (2026-08-07), both needed to fully kill a white flash on pop in dark mode: the root `Stack`'s `screenOptions` sets `contentStyle: { backgroundColor: colors.background }` — `react-native-screens`' native Screen surface defaults to white regardless of app theme, so without this, sliding to reveal the screen underneath during a pop (or the brief moment before a freshly-pushed screen's own content has painted) flashed white through the gap. That alone wasn't sufficient (confirmed on-device, e.g. Dashboard → back → Home still flashed) — `contentStyle` only themes react-native-screens' own JS-rendered screen surface, not the native root/window background underneath, which Android still shows through during a transition, especially with `edgeToEdgeEnabled` (no opaque system-bar chrome covers the edges to hide it). `expo-system-ui` was already a dependency but never actually used anywhere; `RootStack` now calls `SystemUI.setBackgroundColorAsync(colors.background)` in a `useEffect` keyed on `colors.background` to keep the native window background themed too. — task-filter icon row, Calendar/Stats/Streaks tabs — kept in the same left-to-right order as `TaskHeader`'s tabs, 2026-08-07, since the two headers previously disagreed on ordering) renders once; only the content below swaps between `DashboardCalendarView`, `DashboardStatsView`, and `DashboardStreaksView` on local `activeTab` state, cross-faded rather than navigated. The tab *order* matches `task-detail`, but which tab opens active doesn't have to (2026-08-07: both screens now restore whichever tab was last viewed, via `SettingsContext`'s `dashboardLastTab`/`taskDetailLastTab` — Dashboard has no deep-linkable tab of its own so it always just restores the last one; `task-detail`'s explicit `tab` search param still wins when present, and viewing via that param never overwrites the remembered preference, only actually tapping a tab does). Before either has ever been switched, they still fall back to their original defaults — Stats for Dashboard, Calendar for `task-detail` — so first-launch behavior is unchanged. The task-filter selection lives in `DashboardScreen` itself (not inside any tab's view) so it filters *everything*, whichever tab is active. None of the custom visualizations across these tabs use `react-native-chart-kit` — none fit its API (per-bar coloring, a frozen-label-column grid, a center-aligned variable-width bar list).
  - `DashboardStatsView` mirrors `TaskStatsView`'s design exactly (same no-card-chrome tiered hierarchy, same chart cards/styling) adapted for a task list instead of one task: hero = Total Completions + "Since {earliest task's createdAt}"; secondary = Current Streak + Best Streak (both `Math.max` across the filtered tasks) — unlike the per-task screen, Current Streak isn't dropped here since there's no header badge already showing it for an aggregate view; tertiary = Rate, Per Week, Best Day (all-time, independent of the chart's own time-range toggle, same reasoning as `TaskStatsView`). Its Activity section (week/month/year/all-time toggle) leads with a per-task-breakdown chart card, **Total Completions** (2026-08-07, moved here from the Calendar tab since it's a per-task breakdown of the same Activity data, so it shares that section's toggle/state directly rather than needing its own; positioned first, ahead of `Completions Over Time`/`By Day of Week`/`By Time of Day`, per explicit user direction) — a custom **horizontal** bar chart (2026-08-07, switched from vertical bars so it grows down to fit however many tasks there are instead of needing horizontal scrolling): one row per task (icon · track · value), bar width proportional to that task's completions within the selected range, filled in its own `task.color`. Each row is tappable (2026-08-07) — navigates to `task-detail` on that task's Stats tab (`?taskId=X&tab=stats`), mirroring `DashboardStreaksView`'s per-streak-row navigation below. This also fixed a real inconsistency in the old layout, where the timeframe picker was wired to *both* the top stats and the charts, but only `totalCompletions` actually recomputed per range (`calculateAggregateStats` reads `currentStreak`/`bestStreak`/`completionRate` straight from each task's precomputed `.stats`, never from the filtered completions it was handed) — so 3 of the 4 old top stats silently ignored the picker anyway; now the headline stats are explicitly all-time and only the Activity section (charts + this bar chart) is time-scoped.
  - `DashboardCalendarView` (renamed from `DashboardReportsView` 2026-08-07 — "this is essentially just the global equivalent to the task calendar view") is the **infinite, full-width calendar grid**: tasks as rows (icon only, in a fixed non-scrolling label column) × dates as columns, most-recent-day-on-the-left (a horizontal `FlatList`, newest at index 0, `subDays(today, i)` going right). It has no timeframe toggle of its own — always "infinite", paginating further into the past via `onEndReached` (grows `loadedDays` by `DAYS_PAGE_SIZE`, capped at the earliest selected task's `createdAt` so it doesn't paginate into empty pre-history) rather than pre-rendering every day in a bounded range upfront. Each cell reuses `PartialDayPie`/`MissedDayMark` and `isDueOnDate` (now exported from `streaks.ts`) — the exact same completed/partial/missed/not-due states as the per-task calendar, just tiny (the missed-day `X` renders with no circle backing, since this grid is dense enough that a solid circle per miss reads as too heavy, at the same `opacity: 0.3` as the dimmed not-due circle — matched 2026-08-07, was a heavier 0.5 that read as more prominent than the not-due dimming it's meant to feel equally muted with). The grid's wrapper cancels the screen's own side padding (`marginHorizontal: -16` + `paddingLeft: 16`) so it can actually scroll to the true screen edge instead of stopping short. Each date column's header is two stacked rows (2026-08-07): a month/year label (`"MMM yy"` — `"MMM yyyy"` doesn't fit the 32px column and gets clipped) that only renders on a month's first day, above the day-of-month number that always renders. The screen has no "Calendar Overview" title above this grid (removed 2026-08-07 as redundant with the tab itself being labeled "Calendar").

The section above this grid is explicitly titled "Timeline" (2026-08-07), with a **Grid | Bars** pill toggle on the same row, right-aligned (`timelineHeaderRow`, `justifyContent: 'space-between'` — the toggle started left-aligned below the title on its own row, moved per explicit user direction). The toggle switches what each day column renders below its shared date header, without remounting or resetting the `FlatList` itself — `data`/`ref`/scroll position/`onEndReached`/`onViewableItemsChanged` are all shared; only the per-item content branches on `mainGridMode` inside the same `renderItem`, so toggling mid-scroll doesn't jump back to today. "Grid" is the original per-task dot grid described above. The label column of task icons is now shown in **both** modes (2026-08-07 — initially hidden in Bars mode since there are no per-task rows to label 1:1, but per explicit user direction it's still useful as a legend of which color/icon belongs to which task, even knowing it won't line up row-for-row with the bar's own stacking order below).

    "Bars" renders one stacked bar per day instead: one segment per task, each segment's height equal to that task's own normalized completion fraction for the day (`min(completionCount, timesPerDay) / timesPerDay`, capped at 1) times `BAR_UNIT_HEIGHT` (== `GRID_CELL_SIZE`, so a day where every task is fully done reaches the exact same total height Grid mode's task rows already occupy — `tasks.length * GRID_CELL_SIZE` — keeping the two modes' vertical scale consistent). Segments stack in normal top-to-bottom `tasks` order (`barStack` has no `flexDirection` override — plain `column`) inside a fixed-height (`tasks.length * BAR_UNIT_HEIGHT`) `justifyContent: 'flex-end'` track, so every day column shares the same max height regardless of that day's own total: `flex-end` anchors the (auto-height, shorter-than-max) stack flush against the track's bottom edge, meaning the *last* rendered segment touches bottom while the *first* task ends up topmost — matching the label column's own top-to-bottom task order (2026-08-07 — an earlier version used `flexDirection: 'column-reverse'` specifically to put the first task at the bottom, but the user found that backwards once they saw it rendered and asked for first-task-at-top instead, which just meant dropping the reversal since `justifyContent: 'flex-end'` alone already anchors the group's *tail* to the bottom regardless of direction). Each day's bar `marginHorizontal: 3`s itself away from its neighbors (2026-08-07, per explicit user direction — bars originally touched edge-to-edge) and each segment is rounded (`BAR_SEGMENT_RADIUS`) with a small `BAR_SEGMENT_GAP` between *visible* segments (`marginTop` on every segment past the first in the *filtered* list — the same `column-reverse` fix that flipped the stacking order also silently inverted which end of each pair the gap-carrying segment was, breaking the gap into "every pair except the bottom one touches" until both were caught and fixed together). A task contributing 0 that day is filtered out of the segment list entirely before mapping (not skipped in place via a `null` return) specifically so the gap logic can be based on position among only the segments that actually render, rather than raw task index.

    **Overshoot bug (2026-08-07):** a day with every task fully completed rendered taller than the track's own fixed height. The `BAR_SEGMENT_GAP` margins between segments are *extra* height on top of each segment's own `fraction * BAR_UNIT_HEIGHT` -- a full day needs `tasks.length - 1` gaps (the worst case, and the only case that reaches the track's max height in the first place), which pushed the total past `tasks.length * BAR_UNIT_HEIGHT`. Fixed by deriving a slightly smaller `barSegmentUnitHeight` (`BAR_UNIT_HEIGHT` minus that worst-case gap total spread evenly across every task) and using *that* for each segment's height instead of the raw `BAR_UNIT_HEIGHT` -- the track's own height stays `tasks.length * BAR_UNIT_HEIGHT` unchanged (still matching Grid mode's scale), but now a fully-completed day's segments-plus-gaps sum lands exactly on it instead of past it.

    Each segment is also narrower than its track (`BAR_SEGMENT_WIDTH = '60%'`, 2026-08-07 per explicit user direction for more horizontal breathing room between adjacent days' bars) and centered via `alignItems: 'center'` on `barStack` -- every segment shares that same width constant, so they stay uniformly the same width as each other regardless of which task or how many are visible that day.

    (2026-08-07: a full-width aggregate calendar above the per-task mini grids — first a single-color heatmap, then a per-task segmented progress bar, plus a month navigator syncing the timeline grid's scroll position — was built, iterated on, and then removed again per explicit user direction ("let's get rid of the overview calendar completely... go back to how it was"). One real, reusable fix survived the rollback: `monthShape` computes `trailingBlanks` via `getTrailingBlankCount` and now actually uses it — the per-task mini grid's cell array is padded out to a full multiple of 7, so a month's short last week no longer falls short. That padding had been added specifically to fix the removed heatmap's own uneven-cell-size bug, but the per-task mini grid shares the same builder pattern and gets the same correctness for free, so it was kept.)

    Below the main grid (2026-08-07), a **responsive multi-column grid of per-task mini month calendars** (`getTaskMonthColumnCount` — same 2/3/4-column breakpoints as `HomeScreen`'s task grid, 2 columns minimum) shows the *currently-scrolled-into-view* month: the main grid's `FlatList` reports its visible day range via `onViewableItemsChanged`, and the middle of that range's month (via `startOfMonth`, only committed to state when it actually changes via `isSameMonth`) drives both the section's `"MMMM yyyy"` title and every task's mini grid, so scrolling the main grid updates this section live. Each card shows the task's icon + name above its dot grid, sized from the card's own measured width divided by 7 (mirroring `TaskCalendarView`'s Year-mode dot grid math) — **floored to a whole pixel** (a fractional dot size, and the fractional sub-pixel left-offsets it produced across a row, made corners anti-alias inconsistently from one dot to the next on Android specifically, not reproducible on web — the dot style also now sets `overflow: 'hidden'`, since a plain-backgroundColor View without it is a second known Android cause of the same inconsistent-corner-rounding symptom) rather than left as a raw fraction. (An earlier version gave this section's column `flex: 1` to fill the remaining row width, which stretched every dot to 100px+ and broke the layout entirely — the fix was measuring the wrapping grid's own width via `onLayout` and dividing by the responsive column count, the same pattern `TaskCalendarScreen`'s Year view already uses for its month cards.) Each mini grid mirrors that same Year-mode dot grid's states (completed/partial/future, no due/not-due or missed distinction) and reuses `getTrailingBlankCount` for its leading/trailing blanks; since every task's mini grid for a given month shares the same blank-padding shape, that shape is computed once, not per task. Tapping a card navigates to `task-detail` on that task's Calendar tab, pre-set to the section's currently-visible month via a `month` search param (`?taskId=X&tab=calendar&month=2026-07-01`) — see the `task-detail` entry below.
  - `DashboardStreaksView` leads (2026-08-07) with a hero/secondary stats block styled identically to `DashboardStatsView`'s no-card-chrome tiered hierarchy: hero = **Best Streak** (gold trophy, the single longest chain's length) with the achieving task's icon + name (name colored in the task's own `task.color`, bold) + its date range underneath — on a length tie (e.g. two tasks both maxing a 7-day week) the *oldest* tied streak wins the tiebreak, rather than showing every tied task; secondary strip = Streaks (count) · Completions in Streaks (sum of every chain's length) · Average Streak (mean length, one decimal) — all computed from the full unfiltered chain list regardless of the list's own sort mode below. Its own tab icon (and this view's empty-state icon) is `fire`, not a generic chart icon. Below that, the color/icon-coded **streak history** list, on its own tab with infinite *vertical* scroll (a vertical `FlatList`, `onEndReached` growing a `visibleCount` slice of the already-computed chain list — cheap since it's just a re-slice, not a recompute; `visibleCount` resets to one page whenever the task filter *or* sort mode changes so pagination state doesn't carry over). A **Recent | Best** segmented toggle (same pill styling as `DashboardStatsView`'s time-range buttons) switches the list's sort between `getRecentStreaks`'s default newest-first order and a re-sort by streak length descending — both operate on the same underlying chain list, no re-fetch. Sourced from `app/utils/reports.ts`'s `getRecentStreaks` — reconstructs the *actual history* of streak runs (not just the current/best counts `calculateTaskStats` returns) by re-walking the same due-day-gate/quota-period segmentation as `calculateDueDayStats`/`calculateQuotaStats` in `streaks.ts` (a failing segment's own bonus days still extend the chain that's ending, same "IncludingClose" reasoning — verified against `streaks.ts`'s own test scenarios for consistency, see `__tests__/utils/reports.test.ts`), but keeping each segment's actual dates instead of collapsing them into aggregate numbers. `getRecentStreaks` filters out any chain with `length <= 1` — a single completed day isn't really "a streak" since nothing was ever strung together; `getTaskStreakChains` itself stays unfiltered as the raw per-task building block in case a future per-task view wants the 1-day chains too. Each row centers a single group — start date · bar (width ∝ streak length, the task's icon/color, length centered inside it) · end date — as one unit rather than pinning the dates to fixed-width row edges (2026-08-07: that left a gap between a shorter-than-max bar and the dates, instead of the dates sitting snug against the bar's own actual edges); the bar's pixel width is derived from the row's own measured width (`onLayout`, matching the app's established measure-then-divide pattern) minus the two date labels' width, not a raw percentage of the full row. Each row is tappable (2026-08-07) — navigates to `task-detail` on that streak's own task's Streaks tab (`?taskId=X&tab=streaks`, `taskId` from `TaskStreakChain.taskId`), mirroring `DashboardStatsView`'s per-row navigation above. Since this same component also renders as `task-detail`'s own Streaks tab (`tasks={[task]}`), tapping a row there just re-navigates to the same task/tab — harmless (opens another instance of the already-open modal) but not specially guarded against, since it isn't a real bug, just a no-op-ish edge case.
**Follow-up (2026-08-10), addressing a standing `TODO.md` item ("Min streak history width to fit icon + 2 digits"): `streakBar`'s width now scales between a real minimum and the row's max width, instead of a flat 0-to-max scale with an arbitrary floor bolted on after.** The old formula, `Math.max(20, (item.length / maxStreakLength) * maxBarWidth)`, scaled linearly from 0 and only floored the *result* at a flat 20px — which wasn't wide enough for the bar's own icon (12px) + gap (4px) + a 2-digit count + its `paddingHorizontal: 8` on both sides, so several genuinely different short streak lengths could all collapse to the same too-narrow-to-fit-its-content 20px bar. New `STREAK_BAR_MIN_WIDTH` constant (`8*2 + 12 + 4 + 16` — the padding/icon/gap sizes read directly off `streakBar`'s own style values, plus an eyeballed ~16px for two digits of `streakBarText`; no live text measurement, same "estimate a known fixed-shape bit of content" shortcut `TaskCard`'s `ESTIMATED_BADGE_SIZE` already uses elsewhere) is now the true floor, and `getStreakBarWidth(length)` linearly interpolates between it (at the *shortest* currently-visible streak, `minStreakLength`) and `maxBarWidth` (at the longest, `maxStreakLength`) — so every visible streak's bar is both guaranteed to fit its own content *and* still visually differentiated by length, rather than several different short streaks all rendering identically. When every visible streak happens to be the same length (`streakLengthRange === 0`, nothing to differentiate), they all just render at the full `maxBarWidth` rather than picking an arbitrary point on a degenerate range. `maxBarWidth` itself is now also floored at `STREAK_BAR_MIN_WIDTH` (previously a flat `24`) so an unusually narrow row never asks the interpolation to squeeze into a range smaller than the minimum bar itself needs. Verified via `tsc`/`eslint`/`jest` (127/127, unaffected — pure layout math, no tested `utils/` logic touched).

**Follow-up (2026-08-10), same day: "that min size is a bit too wide... pretty squeezing tight," per direct user feedback right after.** Rather than just shaving the `STREAK_BAR_MIN_WIDTH` estimate down on its own (which would've left the *actual* rendered padding/gap wider than what the number assumed, risking the real content not fitting the now-smaller minimum), `streakBar`'s own real style values were tightened alongside it — `paddingHorizontal` 8 → 6, `gap` 4 → 3 — with `STREAK_BAR_MIN_WIDTH`'s breakdown updated to match those same reduced numbers (plus the 2-digit text estimate nudged 16 → 14): `6*2 + 12 + 3 + 14 = 41`, down from 48. Since this also shrinks the *real* padding/gap on every bar (not just the shortest ones), the whole streak-history list reads a bit snugger across the board, not only at its narrowest.

  **Bug (2026-08-08): tapping the pill showed square corners instead of the rounded shape.** First (incomplete) fix: added `overflow: 'hidden'` to `chartTypeToggle`, on the theory that Android's touch feedback was painting across the container's full rectangular bounds. Onboarding is contextual, not a separate screen, and purely reactive to live state rather than a stored progression. Five independent hints exist: three on `HomeScreen`'s first task card (state-dependent, see below), plus two single stationary-target hints added 2026-08-07 — `'dashboard-task-filter'` (Dashboard header's task-filter icon row, only shown once there's more than one task to filter between) and `'task-calendar-tap-day'` (task-detail Calendar tab, month view only). `HomeScreen` targets the first visible `TaskCard` (`onboardingTargetTask = filteredTasks[0]`, skipped once every hint has been seen) and derives which hint condition currently matches from that card's own live state — never from history:
- Card showing its `'task'` face and not completed today → `'hold-to-complete'`
- Card showing its `'task'` face and completed today → `'tap-to-cycle'`
- Card showing its `'calendar'`/`'stats'` face (regardless of completion) → `'hold-to-expand'`

`OnboardingHintKey` (in `SettingsContext`) is the union of all five; `HomeScreen` narrows to its own three via a local `HomeHintKey` type (and a `HOME_HINT_KEYS` list gating `allOnboardingHintsSeen`) so its `Record<HomeHintKey, string>` hint-text map and candidate-hint logic don't have to account for the other two, unrelated screens' hints.

`SettingsContext` also persists `dashboardLastTab`/`taskDetailLastTab` (2026-08-07, defaults `'stats'`/`'calendar'` matching each screen's original hardcoded default) — see the `dashboard`/`task-detail` route entries above for how each screen reads/writes them.

`SettingsContext`'s `onboardingHintsSeen: Record<OnboardingHintKey, boolean>` tracks each of the five independently — dismissing or completing one hint's gesture never affects the others, so e.g. dismissing "tap to cycle" still lets "hold to expand" appear once the card is flipped. A hint is marked seen either by tapping its dismiss (×) or by the user actually performing the gesture it teaches: completing the task (`handleLongPressTask`), flipping to a non-task face (`TaskCard`'s `onFlip={(visibleSide: CardSide) => ...}` prop), long-pressing the flipped face to open the full calendar/stats screen (`onLongPressCalendar`/`onLongPressStats`), tapping a task-filter bubble on Dashboard, or tapping a day on the task-detail Calendar tab. Settings' "Replay Onboarding Hints" resets all flags at once and navigates back to Home — with one exception (2026-08-07): if any non-archived task has already been completed today, `'hold-to-complete'` is left seen rather than reset, since replaying "press and hold to complete" wouldn't make sense when the user's clearly already found that gesture. `resetOnboardingHints` takes an optional `preserve` object (merged over the all-false defaults) to support this; `SettingsScreen` computes the check via `tasks.some(t => !t.archived && isTaskCompleted(t))` before calling it.

`app/components/OnboardingHint.tsx` renders the match as a pulsing ring around the real target plus a pointer/tooltip bubble (dismiss button laid out in a flex row next to the text, not absolutely overlaid) — never an abstract demo — with a spring-like pop-in (`Easing.back`) that replays on every distinct hint because callers key the element by the hint's own key, forcing a remount when the shown hint changes. The bubble is a solid, theme-independent accent fill with white text rather than `colors.surface` — a surface-colored bubble blended into the background on both themes, so this one component intentionally opts out of the semantic palette to stay legible everywhere. It defaults to auto-picking above/below the target from the target's own screen position, but takes an optional `placement?: 'auto' | 'above' | 'below'` (2026-08-07) to force one side — used by the Calendar tap-day hint, where auto-placement's below-if-near-top heuristic doesn't account for the bubble's own height and could land it off the bottom of the screen.

Every hint's target is measured via `app/hooks/useOnboardingTarget.ts` (extracted 2026-08-07 from `HomeScreen`'s original inline implementation once two more call sites needed the identical logic): given a `containerRef` and `targetRef` (both plain `useRef<View>(null)`), it measures the target's layout via `measureLayout` *relative to the container* — deliberately not `measureInWindow`, since window coordinates only line up with an absoluteFill overlay's `top`/`left` if the container's origin exactly coincides with the window's, an assumption Android's edge-to-edge status-bar handling breaks (this was a real bug: the ring rendered offset upward into the header before the fix). `onLayout` (react-native-web's `ResizeObserver` polyfill) doesn't reliably fire on initial mount, so a `requestAnimationFrame`-scheduled measurement is the primary trigger; on native Android a single rAF isn't enough either (the native layout pass, or a screen's own slide-in transition, can still be in flight), so it polls on a short interval and stops once two consecutive reads agree layout has settled, capped so a target that never stabilizes doesn't poll forever. `HomeScreen` additionally re-measures on `onScroll` (its target can scroll out from under the ring, unlike the two newer hints' stationary targets) and re-attaches its target ref per-render since the onboarding target task can change; `TaskCard` is a `React.forwardRef` specifically so `HomeScreen` can attach that ref directly to the card's own root `View` (no extra wrapper element — an earlier version wrapped it in a plain `<View>` for measurement, which broke the FlatList grid's row layout). The Calendar tap-day hint's target is the month grid's first actual day cell (`dayNumber === 1`, ref'd conditionally inside `renderItem` the same way `HomeScreen` ref's its one target row) rather than the whole grid or the week-day label row — both tried first and rejected: the whole multi-week grid is taller than the viewport (pushing an "auto"-placed bubble off-screen), and the label row doesn't visually read as "a day" to point at.

Shared state: `app/stores/taskStore.ts` (`useTaskStore`) — single source of truth for `tasks`, persisted to AsyncStorage under key `"tasks"` via Zustand's `persist` middleware (see "State management" below for why this moved off Context). Delegates streak/stat calculation to `app/utils/streaks.ts` (see below). Also exposes `archiveTask`/`restoreTask` (flip `task.archived`, same `updateTask` path) and `importTasks(tasks, { mode, exportMeta })` (`'replace'` or `'merge'`, used by Settings' Import — see below). `getCompletionCount(task, date)`/`isTaskCompleted(task, date)` (today's progress toward `timesPerDay`) are no longer store methods — they're plain functions in `app/utils/streaks.ts`, reading `task.completions` directly. `lastImport` (`{ exportId, importedAt }`) is its own separate tiny store, `app/stores/lastImportStore.ts`, persisted under its own AsyncStorage key `"lastImport"`, so Settings can detect re-importing the same file.

Three extra mutators exist purely to back the toast "Undo" actions described below, and aren't general-purpose:
- `restoreDeletedTask(task)` re-inserts an already-deleted task exactly as captured (same id/completions), appended to the end — position isn't preserved.
- `undoCompleteTask(taskId, date?)` reverses exactly one `completeTask` press: decrements `timesCompleted` if >1, otherwise removes that day's completion entirely. This is distinct from `uncompleteTask` (used by `TaskCalendarScreen`'s tap-a-day-to-clear-it), which always clears the whole day regardless of count — undoing one accidental tap on a multi-rep task shouldn't also wipe out reps logged earlier that day.
- `restoreCompletion(taskId, completion)` re-inserts an exact `TaskCompletion` record (same id/date/timesCompleted), for undoing `TaskCalendarScreen`'s clear-a-day tap — since `uncompleteTask` wipes the whole day, Undo needs the snapshot taken just before that call, not just a single `completeTask` re-add (which would lose a multi-rep day's count).

## State management

(2026-08-08) Migrated `TaskContext`/`SettingsContext` (both deleted) to Zustand — `app/stores/taskStore.ts`, `settingsStore.ts`, `lastImportStore.ts`. Driven by a performance audit that found both contexts handing out a fresh, unmemoized object as their Provider `value` on every render, with no `useCallback` on any mutator/setter — since React Context has no concept of "select a slice," this meant *every* consumer of `useTaskContext()`/`useSettings()` re-rendered on *any* change to that context, regardless of which field it actually read. Concretely: completing one task re-rendered every visible `TaskCard` on Home, not just the one that changed; and — the bigger find — changing *any* setting re-rendered *every screen in the app*, because `useThemeColors()` (called by every screen for its `StyleSheet`) read the whole `SettingsContext` just to get `themeMode`.

**Store shape**: `tasks` stayed a plain `Task[]` array rather than being normalized to `Record<id, Task>`. Every mutator already rebuilds via `prev.map()`/`.filter()`, which preserves the exact object reference for any task that didn't change — so a selector like `state.tasks.find(t => t.id === taskId)` already returns the same reference when that task is unaffected by a given mutation, and Zustand's default per-selector equality (`Object.is`) already skips re-rendering on that basis. No data-shape change needed to get correct selective subscription.

**`completionCache` dropped entirely.** The old `TaskContext` kept a `Map<taskId, Map<date, count>>` rebuilt via a `useEffect` keyed on `tasks` — meaning it lagged one render behind `tasks` itself right after a mutation (a real staleness window, not just a perf cost: `getCompletionCount`/`isTaskCompleted` could report a just-completed task's *previous* state for one render). Replaced with two plain functions in `app/utils/streaks.ts`, computed directly via `task.completions?.find(c => c.date === dateString)` — no cache, no store dependency, callable on any `task` a component already has as a prop. O(that task's own completion count) per call, trivial for a personal habit tracker's realistic data volumes.

**Legacy AsyncStorage shape migration**: Zustand's `persist` middleware wraps stored data as `{ state, version }`, but the pre-existing AsyncStorage keys (`"tasks"` — a bare `Task[]`; `"appSettings"`/`"lastImport"` — bare objects, from the old Contexts' own `JSON.stringify`) predate that envelope. Blindly switching to `persist` would have silently hydrated to each store's empty default state on first launch after the update — indistinguishable from data loss. Each store therefore uses a custom `PersistStorage` (not `createJSONStorage`) whose `getItem` detects the legacy bare shape (an array for `taskStore`, an object with no `.state` key for the other two) and wraps it into the envelope once; every write after that is already in the new shape. All three AsyncStorage key names stayed identical to the old Contexts' — zero data migration for already-installed devices beyond this one-time envelope wrap.

**Selector style**: bulk-consumer screens (that already need most/all of a store's fields — `AddTaskScreen`, `SettingsScreen`, `TaskCalendarScreen`, etc.) use `zustand/react/shallow`'s `useShallow` to keep the same destructuring ergonomics the old Context calls had. Places with only 1–2 fields just call the store hook multiple times with individual primitive selectors instead (e.g. `ArchivedTasksScreen`) — simpler than reaching for `useShallow` when there's nothing to shallow-compare.

**The actual payoff — `TaskCard.tsx`**: `CardTask`/`CardCalendar` (both `React.memo`'d) used to call `useTaskContext()` directly *inside* the memo boundary — memoizing a component only protects against a parent re-rendering it with the same props, it does nothing against a context value the component itself subscribes to changing. Since `task` was already a stable prop (per the reference-preservation point above), the fix wasn't "select this task from the store" — it was removing the store dependency entirely: `isTaskCompleted`/`getCompletionCount` became direct `streaks.ts` util calls on the `task` prop already in hand, and `CardTask`'s `useSettings()` bulk read became three independent primitive selectors (`showTaskName`, `showTaskCounter`, `showCardBackground`), so it only re-renders on those three fields changing, not on e.g. `themeMode`.

That alone wasn't sufficient — `HomeScreen.tsx`'s `renderItem` built fresh inline arrow functions (`onLongPressCalendar`, `onLongPressStats`, `onLongPressTask`, `onFlip`) for every visible card on every render, independently defeating `TaskCard`'s `React.memo` via prop-identity churn regardless of the context fix. Fixed by changing `TaskCard`'s prop signatures to take the task's `id` (e.g. `onLongPressTask?: (taskId: string) => void`) instead of being pre-bound to one task, so `HomeScreen` can hand every card the *same* four `useCallback`-stabilized handlers rather than one fresh closure per card per render. Those handlers read `onboardingTargetTaskId`/`tasks` via `useRef`s updated every render (`onboardingTargetTaskIdRef`, `tasksRef`) rather than closing over them directly — this is what lets the handlers stay genuinely stable (empty-ish dependency arrays) while still always seeing the *current* onboarding target/task list at call time, not a stale one from whenever they were created.

**`useThemeColors.ts`'s one-line fix**: swapped `const { themeMode } = useSettings()` for `const themeMode = useSettingsStore(state => state.themeMode)` — a single primitive selector fixes the app-wide re-render fan-out described above, since every screen's `useMemo(() => createStyles(colors), [colors])` now only recomputes when the resolved theme actually changes, not on unrelated settings changes.

**Hydration gating**: `app/_layout.tsx`'s `AppGate` used to check `isLoaded` from both Context providers before rendering `RootStack` (else a `LoadingScreen`, avoiding a flash of empty/default state before AsyncStorage resolved). Each store now exposes its own `hasHydrated` boolean, flipped via that store's `onRehydrateStorage` callback once its async read completes — the direct Zustand-native equivalent, and `AppGate` just checks all three stores' `hasHydrated` instead. No `<Provider>` wrapping needed for any of the three stores; `TaskProvider`/`SettingsProvider` were removed from `_layout.tsx` entirely (`ToastProvider` stays — `ToastContext` wasn't part of this migration, see below).

`ToastContext` (`app/context/ToastContext.tsx`) deliberately stayed as Context — it's small, ephemeral, non-persisted UI state (the current toast, if any) with few consumers; neither selective subscription nor persistence would meaningfully help there, and its actions (`showToast`/`hideToast`) were already correctly `useCallback`'d.

**Unrelated cleanup from the same audit, folded into the same pass**: `TaskCard`'s `CardCalendar` (the flipped mini calendar face) and `TaskCalendarScreen`'s Month view both used to render their day grid via a `FlatList` with `scrollEnabled={false}` and `numColumns={7}` — `VirtualizedList` overhead (windowing, scroll-event bookkeeping) for a small, fully bounded, never-actually-scrolled grid (35–42 cells). Both converted to a plain array chunked into week-rows and mapped directly, matching the pattern the rest of the app's bounded calendar grids already used (`DashboardCalendarView`'s mini month grids, `TaskCalendarScreen`'s own Year-mode dot grids). `DashboardStreaksView`'s vertical `FlatList` also gained a `getItemLayout` (`STREAK_ROW_HEIGHT = 24 + 12`, since every row is that same fixed height regardless of streak length — only the bar's *width* varies).

**Follow-up audit (2026-08-08): stat/streak/chart-data recalculation.** Two real, concrete finds, both fixed:

1. **`getCompletionCount(task, date)` and `isTaskCompleted(task, date)` were called back-to-back on the same (task, date) pair in six places** (`DashboardCalendarView.tsx`'s `buildMonthRows` and main grid, `TaskCard.tsx`'s `CardTask`/`CardCalendar`, `TaskCalendarScreen.tsx`'s Month/Year views) — `isTaskCompleted` is defined as `getCompletionCount(task, date) >= (task.timesPerDay || 1)`, so calling both meant redundantly repeating the exact same `.find()` scan over `task.completions` a second time for information already in hand from the first call. Fixed by computing `completionCount` once and deriving `isCompleted` from it directly at every one of those call sites.
2. **The calendar grids' per-cell lookups were the bigger issue**: each cell independently called `getCompletionCount`/`isTaskCompleted`, each doing an O(that task's completion count) linear scan — for a grid with `cells × tasks` cells, that's `cells × tasks × completions` scans per render, and since completions are appended in chronological order while these grids show the most *recent* days first, the common case is close to a full-array scan on every single cell (the match is near the end of the array, `.find()` scans from the start). Fixed with a new `app/utils/streaks.ts` export, `buildCompletionCountsByDate(completions): Map<string, number>` — built once per task via `useMemo` keyed on that task's own `completions` reference, giving O(1) lookups after that one-time O(completions) build. Applied in `DashboardCalendarView.tsx` (a `Map<taskId, Map<date, count>>`, keyed on `tasks`, covering both the Timeline grid and the per-task mini month grids — `buildMonthRows` itself stayed a plain per-task function, but now does map lookups instead of array scans), `TaskCalendarScreen.tsx` (single map per task, covering the Month view, Year view, and `handleDayPress`'s pre-mutation count check), and `TaskCard.tsx`'s `CardCalendar` (same pattern, ~31 lookups against one task). `CardTask` didn't need the map — it only ever does one lookup (today), so it kept a direct `getCompletionCount` call and just stopped calling `isTaskCompleted` separately afterward. This is safe against the exact staleness class of bug that killed the old `completionCache` (see "State management" above): each map is a component-level `useMemo` keyed directly on the *current* `completions` reference, not a separately-synchronized store slice, so it can't lag a render behind.
3. **A genuinely missing `useMemo`** in `TaskStatsScreen.tsx`: its `getCompletionPatterns` call for the Activity section's day-of-week/hour-of-day charts ran unmemoized on every render, while the near-identical sibling call for "Best Day" (`allTimePatterns`, a few lines below) was already correctly memoized, and `DashboardStatsView.tsx`'s equivalent aggregate-view call was too — this one screen was just missed. Fixed to match. `chartData`/`dayOfWeekChartData`/`hourOfDayChartData` object literals in both stats screens were also wrapped in `useMemo` (a smaller, referential-stability-only fix, so `react-native-chart-kit` doesn't see a "new" props object on every render that didn't actually change the underlying data).

**Considered and *not* pursued**: `streaks.ts`'s `calculateDueDayStats`/`calculateQuotaStats` (aggregate current/best streak) and `reports.ts`'s `getDueDayStreakChains`/`getQuotaStreakChains` (full streak history) independently re-walk very similar day-by-day/period segmentation logic to derive overlapping information — the former just needs two numbers, the latter needs every chain's actual dates. **Second sweep (2026-08-08), broader than stat/chart recalculation this time — checked every screen/component for missing `useMemo`/`useCallback` and, especially, any inline callback handed to one of the app's six `React.memo`'d components** (`TaskCard`, `CardTask`, `CardCalendar`, `CardStats`, `HomeHeader`, `ParticleSystem` — the only components in the app wrapped in `React.memo`; nothing else has a memoized child for an inline prop to defeat, so most other screens' plain functions/inline closures don't have the same failure mode `TaskCard`'s did). Found one genuine bug this way:

**Real bug found by the user, not this audit (2026-08-08): particles didn't replay on a second streak celebration.** Repro: complete a task (particles show, streak badge flips to fire), Undo (badge correctly reverts to expiring), complete it again (badge correctly flips back to fire, but no particles this time). Root cause was one layer deeper than the props-stability fix above: `ParticleSystem`'s `onComplete` prop was never actually *called* anywhere in the component — genuinely dead code, in both the pre-sweep version and the sweep's own "fix" above (which addressed prop/closure stability but missed that the completion callback itself was never wired up). Since nothing ever flipped `TaskCard`'s `showParticles` back to `false`, the first celebration's `<ParticleSystem>` never unmounted; the second celebration's `setShowParticles(true)` was therefore a same-value no-op (React skips the re-render), so the *same* mounted instance stuck around — and since its particle array only ever initializes once per mount (guarded by the lazy `useState` initializer), no fresh particles were ever generated for the second celebration. Fixed two ways, deliberately redundant so the bug can't recur even if one half regresses:
  - `ParticleSystem` now actually calls `onComplete` — via a plain `setTimeout` sized to the worst-case total particle lifetime (`config.life + config.lifeVariance`), fired once on mount, not tied to any individual particle's own Reanimated completion callback. Same rationale as `TaskCard`'s own completion-pop animation elsewhere in this doc: an animation library's own "finished" callback isn't trustworthy for driving real control flow on Android.
  - `TaskCard` now also keys `<ParticleSystem>` with a `celebrationKey` counter, bumped every time the celebration `useEffect` actually fires (i.e. every genuine transition into the `fire` badge state). This forces React to unmount the old instance and mount a genuinely fresh one on every celebration regardless of whether the `onComplete`/`showParticles` cycle completes in time — `currentStreak` alone can't be used for this, since an undo-then-redo cycle can return to a *previously seen* streak number (5→6→5→6), which wouldn't look like a "change" to a key derived from the number itself.

  While in this file for the fix, also picked off three small non-behavioral performance items noticed alongside it: `ParticleComponent` now splits its `useAnimatedStyle` into a `useMemo`'d static style (`width`/`height`/`borderRadius`/`backgroundColor`/`position` — fixed for a particle's whole life) plus a smaller animated style with only `transform`/`opacity`, so the UI-thread worklet isn't rebuilding untouched properties on every frame tick; `ParticleComponent` itself is now `React.memo`'d (cheap insurance against re-rendering all `count` particles if `ParticleSystem` ever re-renders for an unrelated reason); and the `particles` prop's default value moved from an inline `= {}` (a fresh object every render, silently defeating `config`'s own `useMemo`) to a module-level `EMPTY_PARTICLE_CONFIG` constant.

**Flame-ified the particle burst itself (2026-08-08), per explicit user direction ("more flame-like... swirl a bit like embers... more dramatic and long-living")** — purely visual, no control-flow changes:
  - **Swirl**: each particle now carries its own `perpX`/`perpY` (a unit vector perpendicular to *that particle's own* drift direction, computed once at creation from its already-randomized `driftAngle`) plus `swirlAmplitude`/`swirlFrequency`/`swirlPhase`. `ParticleComponent`'s per-frame `animatedStyle` derives `t = 1 - progress.value` and adds an envelope times a `sin(t·swirlFrequency·2π + swirlPhase)` oscillation, applied along the particle's perpendicular axis — the particle curls side-to-side around its own rising path rather than corkscrewing around a fixed world axis. A small additional flicker (`0.85 + 0.15·sin(t·22 + phase·3)`, multiplied into `opacity`) gives a fast shimmer on top of the main fade, since real embers dim unevenly rather than smoothly.
    - **Tuning pass (2026-08-08), per explicit user direction ("too much... swirl less... more randomized per particle... reverse decay")**: the envelope was originally `sin(t·π)` (a hump peaking mid-life, 0 at both ends) — changed to `t²`, which is ~0 near the start and grows toward the end of life instead, so a particle drifts fairly straight at first and curls more as it winds down, rather than curling most in the middle. Base `swirlAmplitude`/`swirlFrequency` were also both roughly halved (20→8, 2.4→2) while their *variance* stayed close to (or above) the base value itself (`swirlAmplitudeVariance` 12→8, `swirlFrequencyVariance` 1→1.4) — deliberately so, since variance this large relative to the base is what actually produces some particles swirling much more than others, rather than every particle curling by roughly the same reduced amount.
    - **Follow-up (2026-08-08): particles now spawn staggered instead of all at once.** `Particle` gained a `spawnDelay` (randomized once at creation, uniform within a new `spawnWindow` config field, default 250ms); the lazy `useState` initializer sorts the particle array by `spawnDelay` ascending right after generating it, and a `visibleCount` state (starting at 0) is walked up by one `setTimeout` per particle scheduled at its own `spawnDelay` — the render then just slices `particleState.slice(0, visibleCount)` rather than mapping the full array, so particles literally aren't rendered (and don't start their own life/fade `useEffect`) until their own moment arrives. Sorting once up front means the staggering effect can walk the array in order without re-sorting per timer fire. `ParticleSystem`'s own `onComplete` worst-case timeout grew to account for this: `config.spawnWindow + config.life + config.lifeVariance`, since the *last*-spawned particle's own full lifetime now starts that much later than mount.
  - **More dramatic**: `count` 12 → 18, `size`/`distance`/`driftDistance` and their variances all increased, and `driftAngleVariance` 0 → 20° (particles now splay slightly off pure-vertical instead of every one going perfectly straight up) so the burst reads as fuller and more energetic. Color went from a single coral-red (`#FF6B6B`) lightened/darkened per particle to a `colors: string[]` palette (`ParticleConfig` gained this as an optional field, `getRandomColor` unchanged) — each particle picks one hue at random, then still applies the existing lighten/darken variance on top. First pass spanned deep red through gold (`#FF3B1F`/`#FF6B00`/`#FF9500`/`#FFC300`), which read as too much yellow; per follow-up user direction ("skew red more, to match the theme of red being used for streaks") the palette was narrowed and weighted back toward red — `['#FF6B6B', '#FF6B6B', '#FF3B1F', '#FF3B1F', '#FF6B00']` (duplicated entries bias `getRandomColor`'s random pick), reusing `#FF6B6B` specifically since it's the same red `TaskCard`'s own streak-badge "fire" state already uses (`getStreakBadgeStyle`), with no true yellow/gold left in the mix — just occasional darker-red/orange accents.
    - **Follow-up (2026-08-08): "more vibrant" red/flame colors.** `#FF6B6B` (the streak badge's own red, reused above for thematic consistency) turned out to be a fairly light, muted salmon (~71% HSL lightness) rather than a punchy red, and `getRandomColor`'s 50/50 lighten/darken swing (`colorVariance: 12`) pushed it toward pastel about half the time. Plain RN `View`s have no `mix-blend-mode`/`background-blend-mode` equivalent — true additive blending (`BlendMode.Plus`) would mean rendering particles on a `react-native-skia` `Canvas` instead, a real architecture change (new native dependency, particles off the View tree, likely needs a custom dev client since Skia isn't in Expo Go) — flagged as an option but not pursued yet. Went with the cheaper approximation instead: each `ParticleComponent` now renders a second, larger (`GLOW_SIZE_MULTIPLIER = 2.5`), same-colored circle behind the main one at a capped opacity (`GLOW_OPACITY_CAP = 0.35`) — not a true blur (no blur filter, just a bigger soft-edged circle at low opacity), but reads as a warm halo at this scale. The glow's static size/position (`glowStaticStyle`) offsets itself by `(glowSize - particle.size) / 2` so it's centered on the same point as the particle despite being bigger.
    - **Follow-up (2026-08-08): overall size was too big once the glow was added.** The 2.5x glow multiplier was applied to the *same* `size: 13, sizeVariance: 9` core used before the glow existed, so the visible footprint (core + glow) ballooned well past the original particle size. That first pass then read as too small — nudged back up to `size: 9, sizeVariance: 6` (between the original 13/9 and the overshot 7/5).

    - **Follow-up (2026-08-08): particles now grow in fast rather than appearing instantly at full size.** Scale had been driven entirely by `progress` (`{ scale: progress.value }`, 1→0 over the particle's whole `life`), so a particle was always at its full size the instant it mounted. Added a second, independent shared value, `growth` (starts at 0, `withTiming(1, { duration: GROWTH_DURATION = 120, easing: Easing.out(Easing.cubic) })`, fired in the same mount effect as `progress`'s own countdown), and changed the wrapper's `scale` transform to `growth.value * progress.value`. `GROWTH_DURATION` is a small fraction of `life` (1000ms+), so drift/swirl (still governed by `t = 1 - progress.value`, tiny this early) stay negligible while growth plays out — no need to delay the main life countdown itself to get "grow in, then drift off and die out"; the two just run in parallel and the short growth window naturally reads as a distinct beat before the rest takes over.
    - **Follow-up (2026-08-08): faster grow-in, and opacity now guaranteed to start at true 100%.** `GROWTH_DURATION` 120→70ms. Separately, the flicker formula (`0.85 + 0.15·sin(t·22 + phase·3)`) wasn't actually guaranteed to equal 1 at `t = 0` for every particle -- with a random `phase`, some particles' opacity started as low as 0.7 rather than fully opaque, which read like growth was fading *in* opacity too rather than being purely a size effect. Fixed by switching to `cos` and moving the per-particle variety from a phase *offset* to a frequency multiplier instead (`0.85 + 0.15·cos(t·(18 + phase·2))`) -- `cos(0) = 1` regardless of what `phase` is, so `flicker` (and therefore opacity, since `progress.value` is also 1 at spawn) is now exactly 1 at the start for every particle, while still flickering at a per-particle-unique rate as `t` increases.

Per explicit user direction ("opacity will handle the fading out, I just want it to fade to deeper red colors"), every `glowColorPairs` cooled end was brightened to the same deep-red-but-readable territory `colorPairs` already uses (`#C62828`/`#B71C1C`/`#D32F2F` — no color darker than that), so darkening is now opacity's job alone, not the color itself.

Math.min(currentStreak / bestStreak, 1) : 0` — 100% now means "matching or beating your personal record," and lines up exactly with `isBestStreak` (the same condition already driving the `BEST!` label and gold trophy) rather than an arbitrary unrelated threshold. `currentStreak`/`bestStreak` were also pulled into local variables at the top of `CardStats` (previously `task.stats?.currentStreak || 0` was repeated inline four separate times) to keep the new fraction calc and the existing icon/label JSX from re-deriving the same optional-chained values.

**`TaskHeader` now shows a frequency badge (2026-08-09), per explicit user direction ("a nice clean succinct badge/label, readable more than technical").** New `app/utils/formatFrequency.ts` export, `formatFrequencyLabel(task: StreakScheduleInfo): string`, turns the raw schedule fields into a short human phrase instead of the underlying data model's own terminology — no `"specific_days_of_week"`/`"days_per_month"` anywhere in the output, no raw day-index arrays:

`app/context/ToastContext.tsx` (`useToast().showToast({ message, action?, duration? })`) + `app/components/ToastBanner.tsx` (rendered once at the root, in `_layout.tsx`, as a sibling of `AppGate` — so it overlays every screen and survives navigation) replace `Alert.alert` as the app's default feedback mechanism. Only one toast shows at a time; a new one replaces whatever's currently up. The banner is a solid, theme-independent dark bar with white text and an accent-colored action label, same reasoning as `OnboardingHint`'s bubble — needs to read clearly regardless of the current theme. The policy, per the user's explicit direction (2026-08-07): **no modal confirmations** — perform the action immediately and offer "Undo" via toast — for every action *except* Archive/Delete Task, which the user asked back into an `Alert.alert` confirm specifically because they now live at the bottom of the Edit Task form (denser, easier to mis-tap) rather than their own dedicated screen. Concretely:
- **Complete a task** (`HomeScreen.handleLongPressTask`) → toast + Undo (`undoCompleteTask`).
- **Toggle a day on `TaskCalendarScreen`** (tap a day to complete/clear it) → toast + Undo either way: completing uses `undoCompleteTask`, clearing snapshots the day's `TaskCompletion` before calling `uncompleteTask` and restores it via `restoreCompletion` (needed for multi-rep tasks, where clearing loses a `timesCompleted` > 1 that a plain re-complete wouldn't recover). Originally left off the calendar on the reasoning that tapping again was already its own undo, but the user asked for it back in for consistency with the rest of the app (2026-08-06).
- **Delete / Archive Task** (`AddTaskScreen`, editing mode only) → `Alert.alert` confirm first, *then* toast + Undo (`restoreDeletedTask` / `restoreTask`) after — belt-and-suspenders for anyone who confirms on autopilot. Restoring an archived task doesn't get a toast; re-archiving is the obvious reverse action, always one tap away.
- **Import Data** → no more merge-vs-replace `Alert.alert` prompt. "Import Data" always merges; "Import & Replace All Data" is its own explicit, separately-labeled Settings row (destructive-red icon/text). Either way the full previous `tasks` array is snapshotted before `importTasks` runs, so the toast's Undo is just `importTasks(previousTasks, { mode: 'replace' })` regardless of which mode the original import used. The old "this file looks newer/older/already-imported" advisory copy (which existed to inform the pre-action Merge/Replace choice) was dropped since that choice no longer happens at runtime; "already imported before" now folds into the post-import toast message instead.
- **Export, validation errors, generic failures** → plain info toast, no action — these were always single-dismiss notices, never true confirmations, so converting them was just consistency cleanup.

**Web-testing caveat:** `Alert.alert` (the Archive/Delete confirm) is a no-op on react-native-web in this project's setup — tapping Archive/Delete in a web build shows nothing and does nothing (verified: neither the task's `archived` flag nor its existence changes), rather than silently skipping the confirmation and acting anyway. This isn't a bug introduced here; react-native-web simply doesn't implement native `Alert.alert`. It works normally on Android (the actual target platform). Do one manual smoke test on-device: Edit Task → Archive Task / Delete Task → confirm the modal appears and both Cancel and the destructive action behave as expected.

**A real bug this surfaced (fixed, worth knowing about):** every `TaskContext` mutator used to read the `tasks` array via closure. That's fine for handlers invoked synchronously off a fresh render, but toast "Undo" actions are captured once and invoked *later* — by then the closure's `tasks` could predate the very state update the undo is supposed to reverse (e.g. `undoCompleteTask` couldn't find the completion it was told to remove, since its closure was from before `completeTask`'s update had landed). Fixed by having every mutator build its next array from `saveTasks`'s functional-updater `prev` parameter instead of the outer `tasks` variable — see `withUpdatedStats` and the `saveTasks(prev => ...)` pattern used throughout. Caught by manually driving the full press-toast-undo cycle in a browser rather than just checking the toast rendered.

`expo-haptics` (2026-08-07 — installed since the project's start but unused until now) is called directly at each interaction site rather than wrapped in a shared helper — every call site already needed a different feedback type/style, so a wrapper would just be a thin pass-through. Scoped deliberately to *meaningful* moments (completions, destructive confirms, the long-press gesture threshold, undo) rather than every tap — routine navigation (FAB, header buttons, filter bubbles, tab/toggle switches, month navigation, Dashboard row taps) intentionally has none, to avoid it reading as spammy. ## Accessibility

(2026-08-07) `accessibilityLabel`/`Role`/`Hint`/`State` added across every screen and component — previously nowhere in `app/`, so icon-only buttons (most of the app's header buttons, FAB, steppers, toggles) were silent to screen readers. General approach:
- Every icon-only `TouchableOpacity`/`Pressable` got an explicit `accessibilityLabel` describing the action (e.g. "Back", "Settings", "Decrease days per week") rather than relying on the icon glyph, which screen readers can't interpret.
- Mutually-exclusive toggle groups (frequency type, theme mode, Grid/Bars, Month/Year, time-range pickers, sort toggles) use `accessibilityRole="radio"` + `accessibilityState={{ checked }}`; independently-toggleable sets (day-of-week picker, Dashboard's task filter bubbles) use `accessibilityRole="checkbox"` + `accessibilityState={{ checked }}` instead, since more than one can be active at once. Screen/section tab bars (`TaskHeader`, `DashboardScreen`'s Calendar/Stats/Streaks) use `accessibilityRole="tab"` + `accessibilityState={{ selected }}`.
- Color/icon swatches (`ColorPicker`, `IconPicker`) have no visible text at all — `ColorPicker` labels each swatch by its hex value (`Color #EF4444`; no color-naming data exists at runtime, only as source comments on `DEFAULT_COLORS`/`EXTENDED_COLOR_BATCHES`, so this was the honest option short of a larger data-model change), `IconPicker` labels each by its icon name with hyphens turned to spaces (`run-fast` → "run fast").
- Tappable list/card rows that navigate elsewhere (Dashboard's Stats bar-chart rows, Streaks history rows, the per-task mini calendar cards, Archived Tasks rows) get a combined `accessibilityLabel` (task name + the relevant stat) plus an `accessibilityHint` naming the destination ("Opens this task's stats").
- `TaskCard`'s main `Pressable` is the hardest case: the same physical control tap-flips between task/calendar/stats faces *and* long-press-completes or long-press-opens-the-full-screen, and a physical long-press isn't a standard screen-reader gesture (VoiceOver/TalkBack's own double-tap already maps to `onPress`/flip). Solved with a custom `accessibilityActions` entry (labeled dynamically per visible face — "Mark complete" / "Open full calendar" / "Open full stats") routed through the *same* `handleLongPress` the physical gesture calls via `onAccessibilityAction`, so the two stay in sync automatically without duplicating logic.
- `ToastBanner` announces itself via `accessibilityLiveRegion="polite"` + `accessibilityRole="alert"` so a screen reader picks up a new toast without the user needing to manually navigate to it; its Undo button gets `accessibilityRole="button"` + a label matching its visible text.
- `TaskCalendarScreen`'s Month-view day cells get a full spoken state (`"Monday, January 5, Completed"` / `"...2 of 3 completed"` / `"...Missed"`) plus `accessibilityState={{ disabled: isFuture }}`, since the visual encoding (solid fill / pie wedge / X mark / dimmed) carries no equivalent information otherwise.
- Native `Switch` components (`SettingsScreen`) already announce their own on/off state as a platform control, but needed an explicit `accessibilityLabel` matching their row's text — a `Switch` and its neighboring `Text` aren't programmatically associated otherwise, so without one a screen reader would only announce "on"/"off" with no idea *what* was toggled.

Touch targets: `AddTaskScreen`'s day-of-week buttons and the three +/-/stepper pairs (days/week, days/month, times/day) were 36×36 and 32×32 respectively — both below iOS HIG's 44×44pt minimum. Bumped to 44×44 (radius adjusted to stay circular); the day-of-week row still fits 7 buttons across a standard phone width with `justifyContent: 'space-between'`, just with less slack than before.

`app/utils/streaks.ts` — frequency-aware streak engine, extracted from `TaskContext`:
- Filters completions to "qualifying" ones first (`timesCompleted >= task.timesPerDay`) — a partially-logged day doesn't count.
- `daily` / `specific_days_of_week`: a streak only *breaks* on a missed **due** day, but every day completed — due or not — adds to the running count (2026-08-07, per explicit user direction: previously non-due days were just skipped/ignored entirely, worth neither credit nor blame). Internally this walks every calendar day (not just due days) into segments that each end at a due-day "gate": hitting the gate links the whole segment's day-count into the streak, missing it resets the chain going forward — but the segment that closes on a miss still keeps its own bonus days in `bestStreak`/`lastStreak` up to (not including) the actual miss, rather than losing them entirely; only the *next* segment starts the new `currentStreak` from zero. A due day that's today and not yet completed isn't a miss yet — its trailing days are held as a "pending" segment that's still provisionally counted (e.g. completing Sat/Sun ahead of Monday's gate counts immediately rather than waiting for Monday to resolve). For `daily`, every day is its own due day, so this degenerates to the simple one-day-per-segment case with no non-due days to add.
- `days_per_week` / `days_per_month`: the streak unit is the period (week/month) — a period counts as "met" once enough distinct qualifying days land in it, including mid-period for the current one (so hitting the weekly quota early still keeps the streak alive without waiting for the week to end). A period that fails its quota still contributes its own days to the run that's ending (same "tail stays counted up to the miss" idea as due days above) — it just doesn't link forward, so the next period starts fresh. Status only flips to `'expiring'` once every remaining day of the still-open current period — including today, if today's own chance hasn't been used yet — would be *required* to still reach quota (2026-08-07, per explicit user direction: e.g. needing 1 more day only turns urgent on the period's last day; needing 3 more turns urgent once exactly 3 days remain). Comfortable slack short of quota still reads as `'up_to_date'`, not `'expiring'`.

Data model (`app/types/index.ts`):
- `Task`: id, name, icon, color, `frequency` (`daily | specific_days_of_week | days_per_week | days_per_month`), `daysOfWeek`, `daysPerWeek`, `daysPerMonth`, `timesPerDay`, timestamps, optional `archived`, `stats`, `completions`
- `TaskCompletion`: id, taskId, `date` (yyyy-MM-dd, the day it counts for), `completedAt` (actual timestamp), `timesCompleted` (increments per press up to `timesPerDay`, rather than one record per press)

`app/utils/data.ts` holds pure chart/date-range helpers (time-frame bucketing, day-of-week/hour-of-day histograms, aggregate stats) used by Dashboard and per-task Stats screens.

Three smaller pure-logic modules were pulled out of component files specifically so they're unit-testable (components themselves aren't unit-tested — see Testing above): `app/utils/periodStats.ts` (`getExpectedPeriodTotal` — the frequency-aware "x/N" quota math behind TaskCard's "This week"/"Past 30 days" boxes), `app/utils/pieWedge.ts` (`buildPieWedgePath` — the SVG path geometry behind `PartialDayPie`'s clockwise wedge), and `app/utils/calendarGrid.ts` (`getTrailingBlankCount` — the leading/trailing blank-cell padding math shared by the calendar grids in `TaskCard`'s flipped face and `TaskCalendarScreen`).

**Partial-day fill now carries "heatmap" strength (2026-08-07):** every calendar's partial-completion fill used to be one flat opacity regardless of how close to done a >1x/day task's day actually was (1-of-3 reps read identically to 2-of-3). `PartialDayPie` (the wedge used by `TaskCard`'s flipped calendar face, `TaskCalendarScreen`'s Month view, and `DashboardCalendarView`'s main grid) now sets its fill `opacity` to `Math.max(0.35, fraction)` instead of a flat `0.35` — the wedge angle already encoded the fraction, opacity now reinforces it instead of staying constant. The two flat-opacity dot grids that don't use `PartialDayPie` (`TaskCalendarScreen`'s Year view `yearDot`, and `DashboardCalendarView`'s per-task mini month grid `monthGridDot`) got the same treatment directly on their own partial-state style (`opacity: Math.max(0.35, fraction)`), each needing a `fraction` field added to their per-day cell type since neither previously computed one (only the boolean `isPartial`). The 0.35 floor is kept from the original flat constant, so a bare sliver of progress still reads clearly rather than fading to near-invisible. `TaskCard`'s own front-face today's-progress ring is deliberately untouched — it's a separate `AnimatedPath`, not `PartialDayPie`, and isn't a calendar.

**Soft-skip vs. hard-miss calendar indicators (2026-08-09), per explicit user direction.** Every calendar previously rendered any empty past day the same way (`MissedDayMark`'s hand-drawn X, in `colors.textTertiary`), regardless of whether that day actually broke the streak. Two real gaps: `TaskCard`'s `CardCalendar` and `TaskCalendarScreen`'s Month view computed `isMissed` as plain `isPast && !isCompleted && !isPartial` with **no due-day check at all** — so even a `specific_days_of_week` task's genuinely non-due days showed a hard-miss X (only `DashboardCalendarView`'s main grid was due-aware, via `isDueOnDate`, and even that one still showed an X for every empty day on `days_per_week`/`days_per_month` quota tasks, since `isDueOnDate` returns `true` unconditionally for those frequencies — it only special-cases `specific_days_of_week`). The deeper issue: quota-based frequencies evaluate success at the *period* level (see `calculateQuotaStats`), so no single empty day on those is ever really "the" miss the way a missed due day is for `daily`/`specific_days_of_week`.

`canDayBreakStreak` went through **two** wrong designs before landing on the right one — both corrections came from the same user, each pointing at a real conceptual gap rather than a bug in the arithmetic:

1. **First pass**: `false` unconditionally for both quota frequencies ("quota is decided at the period level, so no single day is ever *the* miss"). Corrected — a quota period absolutely can have real hard misses, just not on a fixed per-day schedule the way due-day gating does.
2. **Second pass**: custom per-day "capacity" math — walk the day's own period, sum what's already banked before it plus every day still available after it, and call it a hard miss once that total can't reach quota anymore. This was internally consistent and heavily tested, but per explicit user redirect it was the wrong *shape* of solution: *"We already had all the logic to calculate streaks, we shouldn't need all this additional logic, just fill the connection spaces with a dash rather than an X."* Concretely, it also produced the wrong real-world result — a currently-losing week/month mostly showed dashes (capacity math only turns to X once quota becomes mathematically unreachable, which for a generous quota can be very late in the period), when the user expected a genuinely failed period to read as mostly/entirely X.

**Final design**, entirely reusing the existing streak-history machinery instead of inventing new logic: `canDayBreakStreak(task: Task, date: Date, chains: StreakChain[]): boolean` now lives in `app/utils/reports.ts` (moved from `streaks.ts` — it needs `getTaskStreakChains`, defined in `reports.ts`, which itself imports from `streaks.ts`; keeping `canDayBreakStreak` in `streaks.ts` would have made that a circular import). For `daily`/`specific_days_of_week` it's unchanged — still just `isDueOnDate` (a missed due day always breaks, a non-due day never can, regardless of streak history). For `days_per_week`/`days_per_month`:
- A day is a **soft skip (dash)** if it falls inside the span (`chain.startDate`–`chain.endDate`, inclusive) of any chain `getTaskStreakChains` already reconstructs — the dash literally connects two real days that are part of the same run, exactly matching the user's framing.
- Or if it falls inside the **current, not-yet-elapsed period** of a streak that's still alive right now (`task.stats.currentStreak > 0`) — `getTaskStreakChains` only reflects periods that are already *decided*, so a current period that hasn't reached quota yet (but hasn't run out of time either) won't appear as a chain yet even though it isn't broken; `task.stats.currentStreak` already carries the correct "don't judge a period before it's over" logic from `calculateQuotaStats`, so it's the source of truth for this "pending tail" case (per the user: *"we will have a tail on pending streaks... the current week/month is not yet over"*).
- Otherwise it's a **hard miss (X)** — before the task's first-ever completion, or in the dead space after a streak has actually broken, matching *"we shouldn't have dashes before at least 1 completed day."*

Verified against the real demo dataset (`demo-data/streakaholic-demo-data.json`, via a throwaway `tsx` script printing a full mark-by-mark day string per task) before considering this done: an `expired`/`never_started` task now shows a solid run of X's for the entire dead stretch since its last real chain ended, a currently-`up_to_date` task's ongoing streak dashes cleanly through to yesterday, and a day inside an old closed chain still reads as connected regardless of that chain's own period having ultimately failed or succeeded.

**Performance note**: `getTaskStreakChains` walks a task's *entire* completion history, so calendar grids memoize it once per task (`useMemo(() => getTaskStreakChains(task), [task])` in `TaskCard`/`TaskCalendarScreen`; a `Map<taskId, StreakChain[]>` in `DashboardCalendarView`, mirroring its existing `completionCountsByTask` pattern) and pass the result into `canDayBreakStreak` per cell, rather than letting the function recompute chains itself on every single empty-day evaluation across a grid.

**Follow-up (2026-08-09): the skip line now visually connects across consecutive days, and shows the day number faded behind it where numbers are shown, per explicit user direction.** `SkippedDayMark.tsx` was rewritten from a small hand-drawn SVG `Line` (fixed `size`, inset within its own little box) to a plain `View` bar that stretches to `width: '100%'` of whatever cell it's given — a straight rectangle has no icon-font baseline-offset concerns to fight (unlike `MissedDayMark`'s X, which is still SVG for that reason), so there was no reason to keep it SVG-based once the goal was "fill the available width" rather than "draw a precise small glyph."

The real fix wasn't the component, though — it was *where* each screen renders it. All three calendar surfaces had been nesting the mark inside a smaller inner circle (`calendarDayInner`'s `calendarDot`-adjacent slot in `TaskCard`, `gridDot` in `DashboardCalendarView`, `dayContent` in `TaskCalendarScreen`) that's noticeably narrower than the actual day cell and, in two of the three, has `overflow: 'hidden'` on top of that — a `width: 100%` line in there would still get clipped short of the cell's true edges, so consecutive skipped days' lines would never actually touch. Fixed by moving the line out to render full-bleed over the *outer* cell instead:
- `TaskCard.tsx`'s `CardCalendar`: no restructuring needed — `calendarDayInner` isn't clipped and already sizes to (almost) the full cell, so just dropping the old `size` prop was enough for the line to stretch correctly.
- `DashboardCalendarView.tsx`: the skip mark moved from a child of `gridDot` (a small clipped circle) to a new sibling `skippedLineOverlay` — `position: 'absolute'`, filling the full `gridCell` — rendered after `gridDot` so it paints on top. `gridDot` itself still switches to `isSkipped`'s shared `gridDotEmpty` background, same as before, just no longer draws the mark itself.
- `TaskCalendarScreen.tsx`'s Month view: same `skippedLineOverlay` pattern, filling the outer `day` `TouchableOpacity` (not the inner circular, `overflow: 'hidden'` `dayContent`), with `pointerEvents="none"` so the decorative overlay never intercepts the cell's own tap handling. This is also the screen with day numbers, so `isSkipped`'s branch inside `dayContent` changed from rendering `SkippedDayMark` directly to rendering the day number itself at reduced opacity (`skippedDayNumber: { opacity: 0.4 }`, matching the existing `futureDay` treatment) — the line overlay then paints on top of that faded number afterward in render order, so the number shows through faintly *behind* the connecting line rather than being replaced by it. `TaskCard`/`DashboardCalendarView` don't show day numbers at all, so this half of the change only applies to `TaskCalendarScreen`.

None of the three screens had a gap between adjacent day cells in their row layout to begin with (`calendarWeekRow`/`weekRow`/the Timeline grid's column `FlatList` all lay cells edge-to-edge already), so once each line fills its own cell's true full width, neighboring cells' lines meet with no visible seam — reading as one continuous connector strung across a whole streak run rather than a series of isolated dashes.

**Follow-up (2026-08-09): completed days now grow connector stubs too, per explicit user direction ("add a connector line on the filled days... on the first day of a streak there's no left line, on the last day of a streak there's no right line except to connect a gap tail in quota based streaks").** Previously only skipped (dash) days drew a line — a completed day's dot just sat there, so a completed day next to a skipped day left a visible gap between the dot's own (smaller-than-the-cell) edge and the skip line's far end, even though the skip line itself already reached the shared cell boundary.

New `isConnectedDay(task, date, chains, completionCounts)` export in `reports.ts`: true if `date` is completed, or is a soft skip per `canDayBreakStreak`, or is *today* specifically with a live streak reaching into it (`task.stats.currentStreak > 0` — today is never itself marked completed/skipped by any of the three screens, since all three gate on `isPast`, so it needs its own case here). A day gets a **left connector stub exactly when its immediate predecessor is also connected**, and a **right connector stub exactly when its immediate successor is also connected** — deliberately not computed from chain boundaries directly, since checking the two neighboring days' own connected-ness already reproduces every case the user asked for with no special-casing: a streak's first day has a non-connected predecessor (nothing before it, or a hard miss) so it naturally gets no left stub; a streak's last day gets no right stub *unless* the day after it is also connected — which is exactly the quota "pending tail" case (the day after a quota chain's last real completion can still be a soft skip if the current period is still open and alive), so the exception the user called out falls out of the same rule for free rather than needing to be coded separately. One edge case handled explicitly: a *completed* day with no visual neighbor on *either* side (`visualRunStart && visualRunEnd` both true — e.g. a month starting on Saturday, so day 1 sits alone in a mostly-blank first row) previously would have hit both `connectorHalfRight` and `connectorHalfLeft` simultaneously, which conflict on `alignSelf` and would silently resolve to whichever came last in the style array rather than anything intentional. **1. **4. Performance evaluation, per explicit request.** Assessed as negligible:
- The weekday letter is one more cheap `format()` call per rendered column, alongside the day-number format call that already existed — not per task, so it doesn't scale with how many tasks are selected.

This doesn't affect the *horizontal* FlatList's own virtualization/windowing, which keys off width/x-position, not height — it just makes the outer vertical `ScrollView`'s total content taller, a one-time layout cost with no per-scroll-frame implication.

The completion pop's timing and structure (2026-08-07, five passes) went through: its original damping:8/stiffness:100 spring + 200ms fades + 500ms fixed hold (800ms total, carried over unchanged from the pre-Reanimated `Animated` version and never re-tuned — read as a slow, gentle bounce with a sluggish hold); a punchier spring; an explicit-duration three-phase version (150ms pop + 1000ms hold + 450ms return) built specifically to stop depending on a spring's completion callback for control flow (that callback measured 3-4s on Android instead of the few-hundred-ms its damping/stiffness would predict) — abandoned for feeling mechanical, with the 1000ms hold in particular reading as an awkward freeze; a single-action version (`scale.value = 1.2` instant jump, then one `withSpring` back down) that fixed the timing but, per explicit user direction, still didn't match the intended interaction: **the press-and-hold depress and the completion pop were two independent, uncoordinated animations** (`TaskCard`'s own `scaleAnim`, whole-card, reset only on finger-lift; `CardTask`'s `scale`, icon-only, teleporting to a peak with no relation to whatever the outer depress was doing) rather than one continuous "depress → elastic overshoot → settle" motion.

Two follow-up tweaks (still 2026-08-07): `TaskCard`'s own whole-card `scaleAnim` depress — initially skipped on the `'task'` side to avoid compounding with `CardTask`'s new depress — is back to applying unconditionally on both faces per explicit user direction (they wanted *both* the whole-card depress *and* the icon's own elastic pop, not just the icon's). And the return spring's overshoot went through two rounds of retuning: `damping`/`stiffness` alone couldn't make it dramatic *and* fast, because with `mass: 1` (Reanimated's default) settle time is governed almost entirely by `damping` alone, while overshoot amount is capped by how far the value actually travels — `DEPRESS_SCALE` 0.9 → 1.0 is only 0.1 of travel, far too little to ever overshoot dramatically regardless of damping. The fix was an explicit positive `velocity` (an artificial initial kick, independent of that small positional gap — like a rubber band getting snapped rather than a shallow dip falling back into place), which is what actually buys the dramatic overshoot; landed initially on `withSpring(1, { damping: 16, stiffness: 280, velocity: 6 })`, then pushed considerably further per explicit user direction ("MUCH FURTHER") to `{ damping: 26, stiffness: 450, velocity: 14 }`.

That still wasn't dramatic enough on-device — a spring's overshoot from a `velocity` kick is a physics *estimate*, not a guaranteed number, and it evidently wasn't translating to the intended effect regardless of how far the inputs were pushed. The velocity approach was abandoned entirely in favor of something deterministic: `POP_PEAK_SCALE` (a named constant) is now an explicit, fixed target the icon snaps to via `withTiming(POP_PEAK_SCALE, { duration, easing: Easing.out(Easing.cubic) })` — guaranteed to actually reach that value, not an estimate — immediately chained (via `withSequence`, no `withDelay`, no pause) into a separate spring for the settle back to rest.

One more round of feedback (peak "a little too big", settle "too slow/not bouncy enough") landed on: `POP_PEAK_SCALE` 1.6 → 1.4, snap-up `duration` 130ms → 100ms, and — the more important fix — the return spring's `{ damping: 14, stiffness: 150 }` (few, slow, barely-visible wobbles) → `{ damping: 20, stiffness: 800 }`. The key realization: for the settle spring specifically, `stiffness` sets how fast each oscillation cycle is and `damping` sets how quickly those oscillations decay away — independent knobs. High stiffness *with* high damping gives several fast, clearly-visible bounces that still die out quickly, which low-stiffness/low-damping (slow cycles, slow decay) can't produce no matter how those two are balanced against each other.

Yet another round (bounce "cuts off too abruptly", wants it to "keep bouncing" longer, decay "a bit faster" but *without* losing bounce count/size) exposed a second, independent issue: Reanimated's spring config exposes an `energyThreshold` (the combined kinetic+potential energy below which it snaps straight to the target) — its default was cutting the animation over before the decay had visibly finished, reading as an abrupt stop rather than a natural fade-out, regardless of damping/stiffness. Explicitly setting `energyThreshold: 0.0001` (much stricter than default) keeps it animating further into the decay tail before calling itself "at rest". Combined with the insight that real-time-to-settle depends on `damping` alone (not `stiffness`, given `mass: 1`) — so raising `stiffness` further fits *more* oscillation cycles into the *same* real-time envelope, "for free," rather than taking longer — landed on `stiffness` 800 → 1200, `damping` 20 → 22 (a modest bump for slightly faster overall decay, as requested, without sacrificing the bounce count/amplitude gained from the higher stiffness). `COMPLETION_HOLD_DURATION` was bumped 550ms → 750ms to give this now-longer, more complete decay room to actually finish before the checkmark reverts and the completion commits.

(Note: Reanimated's spring config in this version doesn't have the older `restDisplacementThreshold`/`restSpeedThreshold` pair some docs/examples reference — `tsc` caught that immediately as a real type error; `energyThreshold` is the single combined-threshold equivalent here.)

Once satisfied with the shape, a final small "a little over the top" pass (2026-08-07) dialed both dimensions down slightly without touching the overall structure: `POP_PEAK_SCALE` 1.4 → 1.2 (via 1.3), and the return spring's `stiffness` 1200 → 1000 / `damping` 22 → 23 (marginally fewer/smaller bounces, marginally faster decay) — `energyThreshold` and `COMPLETION_HOLD_DURATION` left as-is.

The streak badge's own celebration pop (triggered by the separate `useEffect` watching `streakBadgeStyle?.icon === 'fire'`, not the completion press itself) originally used a much softer, slower two-`withSpring` sequence (`damping: 8, stiffness: 100` both ways) left over from before the icon's own pop went through all of the above tuning — read as noticeably sluggish next to the icon's punchier settle. Deliberately takes resolved `iconSize`/`iconFontSize` as props rather than deriving them from a card-size formula internally — that sizing logic (`showCardBackground`-dependent scaling) is a `CardTask`-specific layout concern, not part of "the icon widget" itself, so `TaskHeader` can pass its own fixed size (96px) without inheriting card-grid assumptions.
- **`app/hooks/useFireCelebration.ts`** (new) — the streak-badge "pop + particle burst" celebration, previously an inline `useEffect` in `CardTask` watching `streakBadgeStyle?.icon === 'fire'`. Returns `{ streakBadgeStyle, badgeAnimatedStyle, showParticles, celebrationKey, handleParticlesComplete }`; both `CardTask` and `TaskHeader` now call this instead of each maintaining their own `badgeScale`/`showParticles`/`celebrationKey` state.

`TaskCard.tsx` itself shrank accordingly (its local `DEPRESS_SCALE`/`POP_PEAK_SCALE`/etc. constants and the icon-animation/badge-celebration `useEffect`s were deleted, not just moved-and-kept) — verified behaviorally unchanged via `tsc`/`eslint`/`jest` (no test coverage exists for component rendering per this project's stated testing scope, so this is a careful line-by-line extraction with the exact original JSX/logic relocated verbatim, not a rewrite).

**1. Streak badge visual emphasis.** Previously a flat `rgba(255,255,255,0.2)` pill regardless of status, with a separately-rendered `clock-outline` icon bolted on for the `expiring` case — a hand-rolled duplicate of the canonical status mapping. Replaced with a direct `getStreakBadgeStyle(task)` call (the same function `TaskCard`'s own front-face badge and `CardStats` already use), so the badge is now colored with the actual status color (red `fire`/orange `clock-outline`/gray `sleep`) instead of staying visually identical across every status. Also sized up considerably (icon 16→22, text 16→20, padding 6/12→8/16, pill radius 16→20) and gained a shadow (`shadowOpacity: 0.2`, `elevation: 3`) for a more "raised" presence against the solid-color header background. Now also runs the same `useFireCelebration` pop-and-particle animation `TaskCard`'s badge does, with its own re-estimated capsule `spawnArea` sized for the bigger badge.

**2. Prev/next task cycling.** `TaskDetailScreen` computes `cyclableTasks` (`tasks.filter(t => !t.archived)`, same store order used everywhere else tasks are listed) and the current task's index within it, and passes `onPrevTask`/`onNextTask` callbacks into `TaskHeader` — omitted entirely (no buttons render) when there's only one task to cycle between. Navigation uses `router.setParams({ taskId: ... })`, not `router.push`, specifically so switching tasks updates the *same* screen instance rather than stacking a new modal on top — this preserves `activeTab`'s local state (you stay on whichever tab you were viewing) and avoids an ever-growing modal stack from repeated cycling. Wraps around at both ends (`(index + length) % length`), since "cycle through tasks" implies wrapping, not stopping at the first/last task. Buttons are `chevron-left`/`chevron-right`, flanking the icon in a new `iconRow`.

**3. Interactive icon.** `TaskHeader` now owns its own `progress`/`isPressed`/`isCompleting` state and a `Pressable` wrapping `TaskProgressIcon`, reimplemented at this screen's level (not by reaching into `TaskCard`/`CardTask` directly, since this is a single large icon in a header, not a flippable card — there's no flip/calendar-face/stats-face concept here). `handleCompleted` mirrors `HomeScreen.handleLongPressTask` exactly: success haptic, `completeTask`, a toast with an `Undo` action wired to `undoCompleteTask`. An already-completed task's icon still renders correctly (solid fill, via `TaskProgressIcon`'s own `completed` check) but press/long-press are no-ops — unlike `TaskCard`'s own already-completed handling (which navigates to `task-detail`), there's nothing further to navigate to since this *is* `task-detail`. A `useEffect(() => setIsCompleting(false), [task])`, identical in spirit to `TaskCard`'s own, guards against stale completion-animation state carrying over when `task` changes out from under the component — both on a real completion (the store mutation swaps in a new task object with updated stats) and when cycling to a different task via the new prev/next buttons.

**Follow-up bug (2026-08-10), reported directly against the real header: the icon was effectively invisible.** `TaskProgressIcon` draws its ring/fill directly in `task.color` — fine sitting on `TaskCard`'s neutral `colors.surface` background, but `TaskHeader`'s own background *is* `task.color`, so the ring (and, while incomplete, the icon glyph itself) rendered in the exact same color as what it sat on. Two candidate fixes were weighed: recolor the icon for this one context (e.g. force white/neutral strokes when on a task-colored background), or give it a neutral backdrop to contrast against, matching how it already works on the card. Went with the backdrop — recoloring would mean the icon is no longer really showing the task's own color the way the card's version does, and would need `TaskProgressIcon` to know about (or be told) whatever background it happens to sit on, complicating a component whose whole value is being a faithful, unmodified reuse. New `iconBackdrop` style — a `colors.surface`-filled circle (deliberately the theme's actual surface color, not a generic white, so it reproduces the exact contrast conditions `DEFAULT_COLORS` were already chosen against — see that array's own comment on being checked against both light and dark surfaces) sized `ICON_SIZE + 20` so it still reads as a visible "plate" around the icon even in the completed state, where the ring's own solid fill circle nearly fills its full bounding box — an exact backdrop/icon size match would leave no visible border between the two. Also picked up a subtle shadow (`shadowOpacity: 0.15`, `elevation: 3`) for a "raised" feel consistent with the streak badge's own shadow treatment added alongside it.

**Tried and reverted (2026-08-10):** per explicit user direction, the backdrop was briefly made semi-transparent (`tinycolor(colors.surface).setAlpha(0.7).toRgbString()` instead of the plain opaque hex string) to soften the "harsh"/stark-cutout look. Rejected on sight ("Nah, don't like that") — reverted back to the plain fully-opaque `colors.surface` fill described above. Worth knowing if revisiting this backdrop again: a straight opacity reduction on `colors.surface` wasn't the right direction here, so a different softening approach (if wanted later) shouldn't just retry the same knob.

**Backdrop removed entirely (2026-08-10), per explicit user direction ("I really don't love the background circle... instead make the icon colors use inverted white (and the header background color) in this context? This also means previous white becomes colored").** Rather than giving the icon a neutral surface to sit on, `TaskProgressIcon` now accepts two optional color props — `color` (defaults to `task.color`, unset for every existing caller so `TaskCard`'s own look is byte-for-byte unchanged) for the ring/fill/incomplete-state icon glyph, and `onColor` (defaults to `'#fff'`) for whatever renders *on top of* a solid `color` fill — the completed-state icon glyph and the checkmark. Every internal `task.color`/hardcoded `'#fff'` reference in the SVG and icon rendering was replaced with `primaryColor`/`onColor` accordingly.

`TaskHeader` now passes `color="#fff"` and `onColor={task.color}` — a genuine inversion of the two roles, not just a different pair of colors: the ring/track/segments/progress-fill/press-hold-sweep all draw in white (visible directly against the header's own `task.color` background, no backdrop needed), and the completed state's solid fill circle becomes a solid *white* circle instead of solid `task.color` — which is exactly why the completed-state icon glyph and checkmark (previously always white, since they always sat on a solid `task.color` fill) needed to flip to `task.color` too, to stay legible against the now-white fill underneath them ("previous white becomes colored", per the user's own framing). The `iconBackdrop` style and its wrapping `View` were deleted outright, not just left unused. `TaskProgressIcon`'s existing `React.memo` and all of `TaskCard`'s own rendering are unaffected, since the new props are optional and every existing call site (`CardTask`) omits them, resolving to the exact same defaults it already relied on.

**Header restructured into two rows (2026-08-10), per explicit user direction, after being asked directly whether the element order made sense.** Previously Back/Edit flanked the *entire* icon+name+frequency+streak-badge stack (`centerContent`) as one tall row, vertically centered against however tall that whole block happened to be — which floated Back/Edit at an inconsistent height (varying per task on whether the streak badge or prev/next chevrons rendered) and left them feeling disconnected from the title itself, unlike every other screen's header. Recommended and implemented splitting it: a slim `headerTop` nav row — Back / task name (`numberOfLines={1}`, `flex: 1`, centered, 18px/700 — sized and weighted to match `DashboardScreen`'s own `headerTitle`, just kept white since this header's background is `task.color` rather than `colors.background`) / Edit — now matches the exact `headerTop` pattern `DashboardScreen`/`SettingsScreen`/`ArchivedTasksScreen` already use, giving Back/Edit a fixed, predictable position pinned to the title rather than to the icon block's own varying height. Below that, `iconSection` centers the icon row (prev/icon/next, unchanged) and a new `badgesRow` — frequency badge and streak badge now sit side by side horizontally under the icon instead of stacked vertically in a column with the (now-removed) title, since the title moved up into the nav row and no longer needs to anchor them. `centerContent`/`titleContainer`/`title` styles were replaced with `headerTop`/`headerTitle`/`iconSection`/`badgesRow` accordingly — no leftover unused styles.

## Free-tier task cap (2026-08-08)

Per `MONETIZATION.md`'s planned Pro tier ("unlimited active tasks" as the main paid lever), a free-tier cap of **6 active (non-archived) tasks** is implemented now, deliberately ahead of the Pro unlock itself — per explicit user direction, shipping the cap before there's anything to buy means it's never a feature taken away from existing users, only ever something the app has always done. `app/utils/taskLimits.ts` is the single source of truth: `MAX_ACTIVE_TASKS = 6`, `getActiveTaskCount(tasks)`, `hasReachedActiveTaskLimit(tasks)` (both operate on the full `tasks` array, filtering out `archived` internally), and a shared `ACTIVE_TASK_LIMIT_MESSAGE` toast string — covered by `__tests__/utils/taskLimits.test.ts`. There was no pre-existing shared "active tasks" helper anywhere in the codebase (every screen inlined its own `.filter(t => !t.archived)`), so this is a new small pure-logic module rather than a refactor of an existing one.

Three real enforcement points, all found by tracing every mutator that can turn a task active or add a new task record (`app/stores/taskStore.ts`'s `addTask`, `restoreTask`, `restoreDeletedTask`, `importTasks`):

1. **`AddTaskScreen.tsx` (creation)** — the actual authority. `atTaskLimit` (`!isEditing && hasReachedActiveTaskLimit(tasks)`, editing never changes the count so it's exempt) disables the Save button and shows an inline `taskLimitText` message below it, mirroring the existing `isNameValid` pattern exactly (memoized boolean gate, disables Save, plus a redundant guard-and-toast at the top of `handleSave` in case the button is somehow bypassed).
2. **`HomeScreen.tsx` (FAB + empty-state "Add a Habit" button)** — both now go through a shared `handleAddTask` that checks the cap *before* navigating, so a capped user gets an immediate toast instead of a dead-end trip to a form they can't submit. (The empty-state button technically can never be at cap — it only renders when there are zero active tasks at all — but routed through the same handler anyway for consistency, at no cost.)
3. **`ArchivedTasksScreen.tsx` (restore)** — explicit "Restore" taps are the one standing (non-ephemeral) path that could otherwise be used to cycle around the cap indefinitely (archive to make room, restore anytime), so it's gated the same way: a `handleRestore` wrapper checks the cap first and shows the same toast instead of calling `restoreTask` directly.

**Deliberately left uncapped, both considered and rejected as enforcement points:**
- **Import (`SettingsScreen.tsx`'s `handleImport`, both merge and replace modes)** — `mergeTaskLists` in `app/utils/importExport.ts` can freely push someone over the cap (any incoming task with a non-matching `id` is added outright, uncapped), but import was left alone on purpose: `MONETIZATION.md`'s free tier explicitly states data export/import are "deliberately never gated... paywalling access to a user's own data would undermine the app's core 'your data is yours' promise." Blocking or trimming an import to enforce the cap would be exactly that. If this creates a real bypass in practice (import as a way around the cap for good), it's a tradeoff explicitly accepted in favor of the data-ownership principle, not an oversight.
- **`restoreDeletedTask` / `restoreTask` as invoked from a toast's Undo action** (in `AddTaskScreen.tsx`'s `handleDelete`/`handleArchiveToggle`) — not gated, since these reverse the user's *own* immediate action within the toast's ~8s window; the only way this could exceed the cap is creating several new tasks in that same handful of seconds right after deleting/archiving one, then tapping Undo — an edge case judged not worth complicating the Undo UX with a possible failure mode for.

Verified via `tsc`/`eslint`/`jest` only (83/83 passing) — not yet confirmed on-device, per the project's standing convention for changes like this.

**Follow-up (2026-08-08): no "free"/"Pro" language in the UI yet, per explicit user direction — there's nothing to upgrade to until Pro actually exists.** `ACTIVE_TASK_LIMIT_MESSAGE` originally read "Free plan supports up to 6 active tasks..."; changed to "You can have up to 6 active tasks. Archive one to add another." — states the limit as just how the app works right now, with no reference to a tier system the app doesn't have yet. The doc-only mentions of "free tier"/"Pro" in `MONETIZATION.md` and code comments (`taskLimits.ts`, explaining *why* the cap exists) are unaffected — this was specifically about user-facing strings.

## Known gaps / bugs (found by reading, not yet fixed)

1. **`TaskCalendarScreen`, `TaskStatsScreen`, and `TaskDetailScreen` all throw synchronously if the task isn't found.** All three do `if (!task) throw new Error('Missing task')` on first render. `tasks` loads asynchronously from AsyncStorage in `TaskContext`, so a hard page reload / direct deep link on web (or a cold app launch landing straight on one of these routes) hits this before `loadTasks()` resolves, showing a crash screen instead of a loading state. Reproducible by navigating straight to `/task-calendar?taskId=...` via a fresh page load rather than in-app navigation. This is also the exact mechanism behind a real, now-fixed crash (2026-08-07): `AddTaskScreen`'s Archive/Delete confirm used to call `router.back()`, which — when this screen was reached via `task-detail`'s pencil icon (a modal pushed on top of another modal) — only popped back to `task-detail`, still holding the just-deleted `taskId`; `TaskDetailScreen`'s own `if (!task) throw` then fired on that re-render. Fixed at the call site by using `router.dismissTo('/')` instead (pops every intermediate modal at once, landing directly on Home), but the underlying fragility in all three screens remains for any other path that could land on one with a stale/deleted `taskId` (e.g. a saved deep link). Fix: show a loading/`null` state while `tasks` is empty-but-still-loading (or the task is genuinely gone), rather than throwing.
2. **`calculateAggregateStats` averages completion rate incorrectly** (`utils/data.ts`): `stats.completionRate = (stats.completionRate + task.stats.completionRate) / 2` run in a `reduce` is a running average that overweights later tasks in the array, not a true mean. Low priority (dashboard cosmetic only).
